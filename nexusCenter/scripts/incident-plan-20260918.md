# 2026-09-18 生产流式故障修复

- 用户已授权线上诊断、修复、部署和收费测试。
- 证据：主机 3.48 GiB 内存、无 Swap、可用约 200 MB；连续采样 I/O wait 94–96%、18–23 个阻塞进程。Java 无容器内存限制，最大堆可占主机 75%；同机运行两个 Java、多套存储服务。25 MB 历史对话发送超时，与 Redis、PostgreSQL 超时同时发生。
- 应急：创建 2 GiB Swap，备份并更新 fstab；启用后 I/O wait 降到 0–6%，六个真实 SSE 测试全部完成，供应商 hzz，重试为 0。不能据此认为所有上游错误已消除。
- 持久化：限制 API JVM 堆与直接内存，为同机数据库、Docker 和文件缓存留空间；设置容器内存上限。减少空闲数据库连接。保持单渠道 90 秒超时、现有供应商和渠道并发业务配置。
- 部署范围：compose.prod.yaml 的 app 配置，复用现有应用镜像；不迁移数据库、不改业务 API。生产原文件备份，配置验证失败自动恢复；就绪检查失败恢复原文件与容器。
- 验证：顺序/并发 SSE、两个文本模型、200 KB/350 KB/1.6 MB/约25 MB 请求、长输出流；要求 response.completed、数据库成功日志、租约释放、临时 Key 撤销。记录长对话测试与真实用户内容不同的限制。
- 回滚：恢复生产 compose.prod.yaml.codex-20260918.bak，docker compose up -d --no-deps --no-build app，然后 nginx -s reload。Swap 可保留；移除时必须先确认内存充足，不能直接 swapoff。

## 追加的已复现问题与最终处理

- 三路约 900 词长输出复现 Responses 渠道并发 2、排队 30 秒后返回 429；将该渠道上限调至 4，保留原 90 秒超时。原记录保存于生产 `/opt/nexusCenter/incident-channel-20260918.json`。回滚只需将该渠道 concurrency_limit 恢复到 2 并递增 version。
- 修改后 3 路长输出全部完成（25.157 / 25.875 / 83.203 秒），首 delta 在 2.328 / 2.969 / 4.344 秒。
- 25,199,069 字节多输入传输测试完成，39.875 秒、无重试、hzz；测试内容为空白填充，不代表原 327 条真实历史的语义复杂度。
- 探索时单字符串 25 MB 触发 JSON 字符串长度限制 HTTP 400；未提高解析上限，改用符合历史输入形式的多项载荷验证。另一次测试客户端 8 秒发送超时已调整测试工具，不能记为平台回归通过。
- 第一轮 6/6 完成；资源配置部署后 12 项探索中 10 项完成、1 项渠道 429（后修复）、1 项测试客户端发送超时。渠道修复后的 3 项长流及 1 项 25 MB 多输入均通过。

## SSE 心跳解析缺陷

- 真实请求在资源与并发修复后仍约23秒报 upstream_connection_failure；新增测试证明 comment/event-only/retry-only SSE 帧触发 map(null) 的 NullPointerException。
- 修改前 3 个心跳测试全部错误；修改后心跳3、路径3、图片编辑兼容2，共8个测试通过。
- 手术式修复 openJsonStream：先 filter(event.data()!=null)，再 map(data)。不改变无业务数据时90秒空闲超时，不伪造完成事件。
- 部署使用生产现有 JAR，仅替换 OpenAiUpstreamClient 类族。校验 public 方法签名不变，以免本地图片编辑新方法与生产源码目录版本差异造成不兼容。保留旧镜像标签与旧 JAR 用于回滚。
