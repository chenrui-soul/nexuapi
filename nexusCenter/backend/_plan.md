# V51：订阅生命周期、积分失效与退款闭环（2026-08-27）

## 本轮目标

- 用户取消订阅后立即停止订阅权限并失效剩余订阅积分。
- 永久余额不受取消影响；在途请求先结算或释放，再计算退款。
- 退款金额按“实付金额 × 可退款订阅积分 ÷ 本周期发放积分”计算，四舍五入保留两位。
- 状态流固定为 `active → refund_pending → refunded`；重复取消幂等。
- 当前只支持显式开启的 Mock 自动退款；正式支付渠道只建立 `pending` 退款记录，等待后续渠道回调。

## 关键实现

- `subscriptions` 增加退款上下文字段，`subscription_refunds` 记录唯一订阅退款单。
- 取消流程先调用 `BillingService.expireSubscriptionCredits`，仅收回订阅限时积分，不触碰永久余额和在途冻结。
- 无冻结时立即完成 Mock/无订单退款；有冻结时由请求收尾或 `SubscriptionRefundScheduler` 逐条短事务扫描。
- 退款上下文读取订单 `payment_provider`：只有 `mock` 才能自动标记订单和订阅为已退款；正式支付保持 `paid`/`refund_pending`。

# V49：订阅分组权限与套餐积分优先扣费闭环（2026-08-26）

## 本轮目标

- 套餐可关联多个服务分组；用户开通时复制为订阅权限快照。
- 活动订阅用户只能使用快照内的服务分组，通用钱包余额不能绕过套餐权限。
- 实扣积分继续按“模型基础用量积分 × 模型时段倍率 × 服务分组倍率”计算。
- 扣费按“当前订阅积分批次 → 其他通用限时积分批次 → 永久余额”执行；不足部分自动拆分。
- 冻结、结算、失败释放、到期和退款均保存批次分摊，退款按原资金来源恢复。

## 架构决策

- **候选 A：钱包增加套餐余额字段**。实现较快，但无法表达多个订阅周期、不同到期时间、跨批次冻结和原路退款。
- **候选 B：积分批次 + 冻结分摊表**。数据结构较多，但能完整处理套餐切换、到期、拆分扣费、并发和幂等。
- **选择：候选 B**。正式计费必须可审计和可逆，不能继续依赖聚合 `expiring_credits` 猜测资金来源。
- **反选原因**：候选 A 会把订阅周期和资金来源压扁成一个数字，到期或退款时必然误伤其他积分。
- **撤销条件**：只有未来将钱包整体迁移为独立复式记账系统，并能覆盖批次冻结与退款来源时才替换。

3. 服务分组可以关联一个或多个供应商，并为每个供应商配置独立、不可回显的上游 APIKey。
4. 同一模型在不同分组可以继续使用不同供应商资源、上游模型名、成本和用户售价倍率。
5. 供应商详情下可以维护上游接口和供应模型；管理侧栏不再出现独立渠道和渠道模型映射入口。

| 并发/竞态 | 管理写入使用 `version` 乐观锁，Gateway 每次选路实时查询供应商状态 | 禁用立即作用于新请求 |

| 降级 | 观测写入失败只记录 request_id；路由配置异常 fail closed | 防止日志故障诱发重复调用 |
| 容量/规模 | 管理列表分页，尝试日志按供应商和时间建索引 | 支持后续聚合 |
| 安全 | 管理写接口要求 Session、CSRF、ROLE_ADMIN；元数据拒绝凭证字段 | 防越权和敏感泄露 |

## 架构决策

### 决策一：模块化单体内新增运行时只读 Mapper

- **候选 A**：Gateway 直接复用管理端 `Admin*Mapper`。
- **候选 B**：`routing` 新增 Gateway 专用只读 Mapper/Service，管理 Mapper 继续只服务后台配置。
- **选择**：候选 B。
- **理由**：运行时查询字段、状态过滤和凭证读取边界与管理 CRUD 不同，独立契约能保持 Controller-Service-Mapper 职责清晰。
- **反选理由**：候选 A 会把管理响应模型、分页逻辑和凭证读取混入高频网关路径。
- **接受代价**：增加少量只读 SQL 和运行时记录类型。
- **撤销条件**：若后续拆分独立 Gateway 服务，可将该只读 Mapper 原样迁移到 Gateway 数据访问层。

### 决策二：Servlet MVC + WebClient 的阻塞首帧准备

- **候选 A**：整个后端切换为纯 WebFlux。
- **候选 B**：保留现有 Spring MVC，非流式请求在 Servlet 线程阻塞等待上游；流式请求先阻塞取得首个 SSE 事件，再交给 `StreamingResponseBody` 持续写出。
- **选择**：候选 B。
- **理由**：现有认证、Session、Controller 和测试均基于 Servlet MVC；首帧准备可以在响应提交前完成路由切换，避免已经输出内容后透明重试。
- **反选理由**：候选 A 会扩大到全项目响应式迁移，超出 Wave 6。
- **接受代价**：首帧阶段占用一个 Servlet 请求线程；流式阶段占用受控异步线程。
- **撤销条件**：网关吞吐和线程占用出现明确压测瓶颈时，将 Gateway 单独拆为纯 WebFlux 服务。

### 决策三：Redis Lua 原子限流

- **候选 A**：Java 分步执行 INCR/GET/EXPIRE。
- **候选 B**：Lua 一次完成 RPM、TPM 预占和 API 令牌/渠道并发占位，失败时不留下部分计数。
- **选择**：候选 B。
- **理由**：多实例下必须保证限流判定与计数变更原子，避免并发穿透和泄漏。
- **接受代价**：Lua 脚本需要独立边界测试。
- **撤销条件**：迁移到专用网关或 Redis 限流组件时替换实现，但键语义和 fail-closed 原则保持不变。
